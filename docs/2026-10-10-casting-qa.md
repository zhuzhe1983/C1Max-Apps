# 无线投屏验证记录

日期：2026-10-10。发送端为 C1 Max 原生 MIPS Linux 应用，接收端为 MacBook 上的官方 Kodi 21.3 ARM64，开启 UPnP / DLNA renderer，不共享电脑媒体库。

## 已通过

- 完整 MIPS 交叉编译、打包与真机部署；安装后校验包内 SHA-256。部署版本为 `20261010-221216-0c502df3`，包含设置 0.3.0、StreamPlayer 0.4.0、Airtune 0.4.0 和 launcher 0.3.2。
- 真机设置页可搜索并选择 MacBook 接收器，800×340 framebuffer 截图确认列表、状态与音量控件正常显示。连接仅建立控制会话，不自动播放内容。
- C1 Max → Kodi：生成的 640×360 H.264/AAC 测试视频正常解码，播放进度推进；暂停、暂停中跳转、保持暂停、恢复、播放中跳转和停止通过。
- C1 Max → Kodi：网络 MP3 广播加载、播放、暂停、恢复、停止以及音量设置通过，测试后恢复接收端原音量。
- C1 Max → Kodi：真实 Emby HLS 视频加载、暂停、暂停中跳转、恢复和停止通过。取流检查为 H.264 **720×404、30fps** 与 AAC；配置的上限为 1280×720，不代表所有源都会输出 720p。
- 安装后实际 StreamPlayer 会话在投屏服务中显示 `playing`、拥有者 `streamplayer-video`，无错误；投屏服务 RSS 约 2 MB。该数值不代表整机总开销，也不是游戏编码性能测量。
- 协议单元测试与 ASan/UBSan 检查覆盖 protobuf 边界、截断包、非法 varint、DNS 压缩循环、URL 验证、XML 转义。
- 本地真实 TLS 接收器测试覆盖分片帧、LOAD 元数据、播放控制、启动失败、首次证书固定、0600 权限与证书变化拒绝。
- Linux daemon / IPC / SOAP 测试覆盖异步控制、UTF-8 元数据、文件权限、拥有者退出、旧进程不能停止新内容、错误保持与恢复、音量、静音、服务退出。
- 既有音频服务、后台播放、音乐 API、全局按键阈值、设置与 StreamPlayer 输入测试通过。应用商店测试确认整包部署后读取实际运行时版本，保留应用隐藏状态，避免使用旧菜单记录误判更新。

## 限制与未完成验证

- **没有开放 NES、其他模拟器或全桌面镜像。** 读取视频编码节点信息期间设备重启，已停止这条探测路径；没有 panic 日志能确定具体原因，不能宣称硬件编码或低延迟游戏投屏已通过。
- 真实 Google Cast 接收器完成 TLS 与状态读取，但启动默认媒体接收应用返回 `LAUNCH_ERROR / NOT_FOUND`，未通过电视端播放验证。根据用户要求停止操作该接收器；之后改测 MacBook DLNA。
- AirPlay / Apple TV 只做发现和未支持提示，未实现配对与播放。
- 真实 Emby 测试使用关闭字幕的流。字幕转码配置、切换会话与位置恢复已接入，尚未完成真实字幕画面对比；其他 DLNA 接收软件和 Jellyfin 仍需分别验证。
- 广播真机测试使用原生协议探针。共享音频服务的电脑端测试通过，但现场应用级探针遇到 launcher 会话切换而没有选中接收器，不能把这次探针当作 Airtune 整条链路验收通过。
- 音量与静音的协议、IPC 和三秒阈值测试通过；没有把模拟请求算作实体长按按键验证。
- 未完成长时间运行、接收端休眠／离线、路由器隔离及所有应用的兼容性测试。
