# C1 Max 无线投屏评估

评估日期：2026-10-10。目标为 Google TV 自带 Google Cast、常见 Android TV 接收 APK，以及 Apple TV 的 AirPlay；不以安装自研电视客户端为前提。

当前状态：已实现原生 Cast V2／DLNA 媒体发送服务、设置入口、StreamPlayer 电视转码档位和共享音频服务接入。**这不是完整的屏幕镜像实现。** NES／桌面镜像与 Apple TV AirPlay 尚未开放。

2026-10-10 真机枚举 `/dev/video1` 时，`v4l2-ctl --all` 在输出设备优先级后失去 ADB 连接；用户反馈机器重启，随后 `/proc/uptime` 确認发生了重启。没有持久化 panic 日志，不能确定具体 ioctl 或断言根因。已停止继续访问编码节点。系统 FFmpeg 未列出 H.264 编码器；固件虽有 `h264e-nl-server`，本次读取进程时它未运行。节点存在不能当作编码测速通过。

已完成的接收端验证：C1 Max → macOS Kodi 21.3 的标准 DLNA，生成的 H.264/AAC 测试视频可解码并完成播放、暂停、恢复、跳转、停止。Google Cast 在真机上完成 TLS 和 GET_STATUS，但现场接收器启动默认媒体应用返回 `LAUNCH_ERROR / NOT_FOUND`，尚未确认电视实际播放。具体测试记录见 [投屏 QA](2026-10-10-casting-qa.md)。

## 可行性结论

| 内容 | 发送方式 | 判断 |
| --- | --- | --- |
| StreamPlayer 视频 | 电视直接拉取兼容的 Emby/Jellyfin 媒体流，词典控制播放 | 优先实现；词典无需再次解码编码，但须处理接收端能力、授权、字幕和播放进度 |
| Airtune／音乐 | 发送音频地址、名称、封面等元数据；必要时有限代理 | 词典计算负担低；具体信息排版由接收端决定，不能保证所有接收器显示完全相同的海报 |
| NES | 从模拟器原始画面取帧，硬编视频并传送游戏 PCM | 有硬件基础，需验证编码器驱动和电视缓冲；可显示不代表延迟适合游戏 |
| PCSX4all／DOSBox | 原始游戏视口＋各自的音频输出适配 | 单独测试资源竞争；NES 的结果不能代替 PS1 或 DOSBox |
| Launcher／其他 UI | 当前显示页的完整画面，或应用声明的有效区域 | 可作为低帧率镜像；全局 framebuffer 无法自动识别所有应用的语义内容区 |

## 硬件与成本

已有真机记录确认 X2000、128 MB RAM、约 100 MB MemTotal，以及 `/dev/video1` 的 `helix-venc`。历史空闲 available 约 45–48 MB，并非运行每个应用时都剩下这么多。此前仅确认编码节点存在，没有证明任意内存画面可成功编码。硬件信息见主仓库 `docs/HARDWARE.md`。

[君正官方规格](https://www.ingenic.com.cn/products-detail/id-15.html)给出 H.264 编码输入 NV12/NV21、最高 1920×1080@30fps。这个上限是芯片规格，不是 C1 Max 固件和网络的实测结果，更不能据此承诺 60fps 投屏。

- 800×340 BGRA 一帧约 1.04 MiB，30fps 原始数据约 32.6 MB/s（261 Mb/s），因此不采用直接发送原始 framebuffer 的方案。
- 同尺寸 NV12 一帧约 0.39 MiB，三个输入缓冲约 1.17 MiB；这只是输入帧，不包括编码器参考帧、DMA、码流、网络、音频及进程开销。
- 游戏优先使用原始帧，避免先放大到液晶尺寸再截图缩小。采用有限队列、异步发送；网络阻塞时丢过期投屏帧，不能阻塞游戏的声音或限速循环。
- 先测 30fps 硬编，不用软件 x264 的泛化性能估计替代真机测量。降帧只影响投屏，不能改变模拟器运行速度。
- 视频、广播让电视直接取流，可避免词典承担实时编码；不能访问媒体源的电视才使用有限代理，不能变成任意 URL 的开放代理。

## 协议和现成项目选择

1. **Google Cast 为主协议。** Google 的发送端 SDK 面向 Android、iOS、Web，没有本机可直接使用的 MIPS Linux SDK。[官方架构](https://developers.google.com/cast/docs/overview)区分发送端和接收端。可参考 [VLC 的 C++ Chromecast 发送实现](https://github.com/videolan/vlc/tree/master/modules/stream_out/chromecast)，按许可证复用必要部分；不把整个 VLC 桌面运行时搬进 128 MB 设备。默认媒体接收器适合 URL 播放，不能视为已经实现低延迟屏幕镜像。实时编码内容可以探索以媒体流发送，接收端缓冲仍须实测。
2. **DLNA / UPnP AV 补充接收 APK 与电视兼容性。** SSDP 发现、AVTransport 控制和媒体 URL 是独立适配器；是否接受直播流、字幕、海报等均按接收端能力处理。[UPnP 标准入口](https://openconnectivity.org/developer/specifications/upnp-resources/upnp/)。
3. **AirPlay / RAOP 单独适配。** 先评估音频与媒体 URL，不承诺完整 AirPlay 屏幕镜像。参考 [pyatv 的发送、配对及元数据实现](https://pyatv.dev/development/stream/)；其文档明确功能有范围，不能据它支持 URL 播放推导出支持游戏镜像。现代 Apple TV 的配对／认证必须单独实现和测试。Python 项目用作协议参考和电脑端对照，不直接作为设备上新增常驻运行时。
4. **通用接收 APK 选 AirScreen 作为首个兼容目标。** [官网](https://www.airscreen.app/index.html)列出 Cast、AirPlay、DLNA、Miracast。产品的协议声明不替代特定 APK 版本和发送端的兼容测试，也不代表开源库或无条件免费。
5. **Connect SDK 用作统一接口的设计参考。** [项目](https://github.com/ConnectSDK/Connect-SDK-Android)已抽象设备发现、媒体与播放控制；Android 版依赖 Android API、Java 和 Google Cast 等模块，不能直接交叉编译成 C1 Max 原生程序。未找到经验证可直接满足本机全部需求的现成跨协议发送库。
6. **Miracast 暂不作为首选。** 它还依赖 Wi-Fi Direct、驱动并发和连接管理；[MiracleCast](https://github.com/albfan/miraclecast)的依赖与本机现有联网方式需要另行验证。支持 Android TV 不等于必然支持 Miracast，也不能把接收端实现当成发送端。

## 全局服务与应用接口

已提供 `设置 → 无线投屏`：搜索设备、选择设备、当前内容、连接状态、电视音量、暂停／继续、断开与忘记。搜索按需异步执行；用户断开后释放媒体服务、编码器和会话锁。未验证的协议或实时镜像能力不能标为“可用”。

由原生 `castd` 管理单个接收会话和协议适配，设置与应用通过本地 IPC 调用。不同应用声明以下内容类型，切换应用时改变发送内容，避免各自维护连接：

- `UI`：完整逻辑屏幕，带方向、当前显示页和有效矩形。
- `GAME`：原始像素帧、像素格式、显示比例、时间戳和游戏音频。
- `VIDEO`：媒体标识／可访问流、字幕、时长、播放位置和元数据。
- `AUDIO`：音频流、广播或歌曲名称、封面和播放状态。

会话必须绑定拥有者和代次：应用退出或崩溃时不能继续显示旧帧；后台音频需要声明由音频服务继续拥有内容。接收端停止、网络断连和用户断开都要反馈给应用。认证资料只保存在设备私有 data，调试输出不记录媒体令牌。

### NES 与其他模拟器

当前 NES 使用 256×240 原始帧，液晶中间实际绘制约 362×340，**不是严格 4:3**。投屏直接从 `WorkFrame` 取图，电视端按 4:3 显示；可先转换成 320×240 方形像素再编码，避免部分接收器忽略像素宽高比。实体提示和虚拟按钮均不进入流。不要直接沿用液晶裁剪结果并假定其比例正确。

音频应从 PCM 生产路径分出，并添加时间戳后编码／封装；读取 framebuffer 不包含音频，也没有证据说明本机具备可直接捕获所有应用声音的 ALSA loopback。NES、PCSX4all、DOSBox 需各自接入。词典扬声器和电视有不同延迟，默认单一声音输出；不把异步双路播放宣传为同步播放。

### StreamPlayer

当前 `client.cpp` 的设备端转码参数为约 400 像素宽、20fps 等低负载档位。电视投送应按接收端能力新建媒体会话／电视档位，不能简单把这个低清地址原样复用后声称高清投屏。默认保持视频本来比例，只发送视频和所选字幕，词典上的按钮留在本机。

电视直接播放时字幕也必须传给电视：优先支持的外置轨道，必要时由媒体服务器烧录。C1 Max 当前本地字幕图层不会自动出现在远程视频中。Google Cast 的 HLS／字幕还需注意[支持格式与 CORS](https://developers.google.com/cast/docs/media)。切换播放方式需要明确暂停本机解码和回收对应的旧转码会话，不能误停止正在由电视使用的流。

### Airtune 与音乐

现有 `shared/audio_client.h` 已有 URL、title、position 和播放状态，可扩展封面与节目元数据。电视直接取电台音频，海报和文字由接收器呈现；精确复刻自定义版式需要专用接收应用，不能作为默认协议的通用承诺。

## 下一阶段的验收门槛

1. 恢复 ADB 后枚举编码器输入／输出格式、尺寸限制、码率和低延迟控制，实际送入生成的 NV12 帧，检查 H.264 可独立解码、时间戳、CPU/RSS/DMA 与关闭后的资源回收。
2. 用本机原生发送端连接 Google Cast 与 AirScreen，完成流加载、暂停、音量、进度、停止、断网和应用退出；Apple TV 另测配对和媒体播放。配对前的服务发现不能算通过。
3. StreamPlayer 和 Airtune 先完成端到端投送，核对字幕、封面、播放状态和凭据边界，再提供设置中的可用入口。
4. NES 同时运行和编码，测本机速度、音频连续性、投屏帧率与按键到电视画面的端到端延迟。若默认接收器缓冲过大，标为观看镜像，不宣称适合在电视上操作游戏；不因芯片有硬编就跳过这一项。
5. 全应用逐个检查有效区域、方向、声音与退出；未适配应用只能使用明确标注的全屏回退。至少包含连续运行、休眠／唤醒和接收端离线测试。

电脑和词典侧已发现 Google Cast、DLNA MediaRenderer、AirPlay/RAOP 服务。AirPlay 仅发现，不进行配对或媒体播放。经用户授权，尝试了指定 Cast 接收器的播放启动；随后改用用户 MacBook 上的 Kodi 测试 DLNA。局域网名称、地址、设备 ID 和原始发现结果不进入公开文档；原始记录留在 `.build/cast-assessment-20261010/`。
